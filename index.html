01Poudy데이터 관리 / 2026.08 – 현재

파일로 관리하던 성분 데이터를 관리자 시스템으로 전환

엑셀과 JSON 파일로 관리하던 성분 데이터를 DB와 관리자 화면으로 옮겼습니다. 이제 승인된 변경만 서비스에 반영됩니다.

문제 원인

  • 성분 데이터 원본은 엑셀 파일 하나였고, AI 검수 결과는 실행할 때마다 JSON 파일로 따로 쌓였습니다. 그래서 지금 확정된 값이 무엇인지 한곳에서 볼 수 없었고, 실제로 두 기록의 태그 상태가 서로 달랐습니다.
  • 팀원과 AI가 같은 엑셀 파일을 열다 보니 프로그램마다 서식이 다르게 보였고, 잠금 파일이 남는 일도 잦았습니다.
  • 서버는 켜질 때 데이터 파일 전체를 읽었는데, 미리 검사하는 단계가 없었습니다. 데이터만 바꿨는데 서버가 켜지지 않은 적도 있습니다.

해결 과정

  • 관리자 화면을 만들었습니다. 원료 22,013건을 이름으로 검색하고, 원료마다 현재 상태와 바뀐 내용, 근거, 수정 기록을 볼 수 있습니다.
  • 화면에서 DB를 바로 고치지 않게 했습니다. 변경은 API 요청으로만 할 수 있고, 요청마다 누가 왜 바꿨는지 남습니다. 같은 요청이 두 번 들어와도 한 번만 반영됩니다.
  • 설정 버전이 맞지 않으면 요청을 거절합니다. 오래된 설정으로 데이터를 바꾸는 일을 막기 위해서입니다.
  • 승인된 변경만 확정 데이터에 넣고, 서비스 스키마에 맞춘 배포용 묶음을 만들었습니다. 이 묶음을 별도 PostgreSQL에 넣고 실제 서비스 조회 코드로 읽히는지 확인했습니다.

결과

  • 엑셀을 직접 열지 않고 관리자 화면에서 조회, 승인, 반영까지 처리
  • 승인하지 않은 값은 반영되지 않고, 같은 요청을 다시 보내도 두 번 반영되지 않음
  • 두 기록이 서로 달랐던 1,086건은 자동으로 고르지 않고 따로 모아 사람이 확인하도록 함
  • 원료 22,013건을 배포용 묶음으로 만들어 별도 DB에 넣고, 다시 넣기와 되돌리기까지 확인
  • 확인 범위는 별도 테스트 DB까지이며, 운영 DB 반영은 아직 하지 않았습니다
02Poudy데이터 파이프라인 / 2026.08 – 현재

파일과 AI 대화로 하던 데이터 처리를 단계별 파이프라인으로 정리

데이터를 원본 보관, 정리와 확정, 서비스 전달 세 단계로 나누고, 단계마다 코드가 할 일과 AI가 할 일을 구분했습니다.

문제 원인

  • 처리 규칙이 파일과 AI 대화 기록에 흩어져 있었습니다. 같은 작업을 다시 돌려도 같은 결과가 나온다는 보장이 없었고, 어떤 규칙으로 처리했는지도 남지 않았습니다.
  • 수집, 정리, 판단, 검토, 반영이 한 흐름에 섞여 있어서 원료 하나에서 막히면 뒤의 작업도 멈췄습니다.
  • 원본과 가공한 결과가 구분되지 않아, 어떤 값이 근거를 갖고 승인된 값인지 나중에 되짚기 어려웠습니다.

해결 과정

  • 데이터를 세 단계로 나눴습니다. 받은 원본은 고치지 않고 보관하고, 다음 단계에서 형식을 맞추고 중복과 충돌을 확인한 뒤 승인된 값만 확정합니다. 마지막 단계에서 서비스 스키마에 맞게 묶습니다. 메달리온 구조를 우리 데이터에 맞게 바꿔 적용했습니다.
  • 단계마다 누가 처리할지 정했습니다. 파일 읽기, 형식 정리, 중복 검사, 배포용 묶음 만들기처럼 답이 정해진 일은 Python 코드가 합니다. 근거 찾기, 설명 쓰기, 검토처럼 판단이 필요한 일만 LLM에게 맡겼습니다.
  • LLM 단계는 LangGraph로 묶어 찾기, 고르기, 쓰기, 검토 순서로 흐르게 했습니다. 사람 확인이 필요하면 멈췄다가, 확인한 뒤 같은 자리에서 이어갑니다.
  • 작업 순서와 재시도는 SQLite로 관리합니다. 시간 초과처럼 다시 하면 풀리는 실패는 잠시 뒤 재시도하고, 다시 물어도 같은 답이 나올 실패는 보류로 돌린 뒤 다음 원료를 처리합니다.

결과

  • 원료 22,013건을 같은 규칙, 같은 순서로 처리하는 구조를 만듦
  • 원본 파일, 원료 22,013건, 태그 코드 98종을 기록해 값이 어디서 왔는지 되짚을 수 있게 함
  • 이미 성공한 AI 호출은 결과를 다시 쓰고, 같은 실패는 반복해서 호출하지 않음
  • 작업 기록을 처음부터 두 번 다시 적용해 같은 상태가 나오는지 확인
  • 확인 범위는 구조 검증과 원료 100건 시험 실행까지이며, 전체 처리는 진행 중입니다
03Poudy인프라 / 2026.08 – 현재

데이터 교체 실패 시 이전 상태로 복구하도록 배포 구성

Docker 이미지를 쓸 수 없는 서버에서 systemd와 CodeDeploy로 배포했습니다. 데이터 교체에 실패하면 이전 데이터로 되돌아갑니다.

문제 원인

  • MVP 단계라 단일 EC2 기반이고 Docker 이미지 저장소를 사용할 수 없어, 컨테이너 이미지 기반 배포를 택할 수 없었습니다.
  • 서비스가 읽는 데이터(JSON)는 S3에 있어서, 애플리케이션 배포와 별개로 데이터 변경을 운영 서버에 안전하게 반영할 경로가 필요했습니다.
  • 웹과 WebView 기반 Play Store 앱이 같은 서버를 쓰기 때문에, 배포나 데이터 교체 중 장애가 곧바로 두 채널의 장애로 이어지는 구조였습니다.

해결 과정

  • Spring Boot JAR와 Next.js standalone 산출물을 EC2에서 systemd 서비스로 직접 실행하고, 프론트 EC2의 Nginx를 HTTPS 단일 진입점으로 두어 /api/*를 백엔드 EC2 사설 IP로 전달했습니다.
  • 운영 배포 경로를 GitHub Actions에서 CodeBuild 빌드 번들과 CodeDeploy 배포 훅으로 옮기고, 서비스 기동 후 health를 검증하도록 구성했습니다.
  • poudy-data-sync.timer가 약 5분마다 S3 변경 여부를 확인하고, 필수 JSON 구조를 검증한 뒤 교체와 재시작을 수행하며 health check가 실패하면 이전 데이터로 롤백하게 했습니다.
  • journald 보존 정책, CloudWatch Agent, Grafana 외부 HTTPS 체크로 로그와 모니터링을 갖췄습니다.

결과

  • www.poudy.site와 Google Play 앱을 이 배포 위에서 운영하며 릴리즈를 이어가는 중
  • systemd 통제 테스트에서 백엔드 프로세스를 강제 종료(SIGKILL)하자 약 5초 후 자동 재시작, 약 24초 후 health 복구 확인
  • k6 고정 부하 60초에서 캐시 미적중 30 req/s 오류 0%, p95 10.97ms, CPU 사용 최대 13%, swap 0을 SSM 지표로 확인해, 지금은 서버를 늘리지 않아도 된다고 판단
04Layer Archive동시성 / 멱등성

동시 요청과 재시도로 발생한 좋아요 오류 해결

동시에 들어오는 좋아요 요청의 경합은 행 잠금으로, 재시도할 때 생기는 상태 변화는 멱등 PUT API로 해결했습니다.

문제 원인

  • "좋아요 존재 여부 확인 → INSERT/DELETE" 사이에 경합이 있어, 같은 사용자의 동시 요청 5개만으로 unique 제약 위반 500이 재현됐습니다.
  • 토글(현재 상태 반전) API는 멱등하지 않아, 응답이 늦어 사용자가 재시도하면 두 번째 요청이 첫 요청이 추가한 좋아요를 삭제했습니다.
  • 클라이언트의 재조회와 지연 재확인 같은 타이밍 기반 완화는 서버 처리가 길어지면 다시 잘못된 재시도를 유도했고, Codex 코드 리뷰에서도 같은 결함이 반복 지적됐습니다.

해결 과정

  • 좋아요 삽입을 REQUIRES_NEW로 분리하던 방식을 걷어내고 같은 트랜잭션에서 처리해, 요청이 실패해도 절반만 반영된 상태가 남지 않게 했습니다.
  • UserRepository.findByIdForUpdate()로 요청 사용자 행에 비관적 락을 걸어 같은 사용자의 좋아요 요청을 직렬화했습니다. 상점 구매와 보상 회수에서 쓰던 패턴과 맞췄습니다.
  • POST 토글을 PUT /like {"liked": true|false} "원하는 최종 상태 지정" API로 재설계하고, setLiked()는 현재 상태와 같으면 아무것도 하지 않도록 했습니다.
  • 실제 Postgres에 동시 요청을 라운드 단위로 반복 전송해 검증하고, 멱등성 통합 테스트를 추가했습니다.

결과

  • 락 도입 후 동일 세션 10개 동시 요청 × 5라운드(50건) 전부 200 성공
  • 같은 liked=true를 10개 동시 × 3라운드 보내도 likeCount가 항상 1로 수렴
  • 재시도가 항상 안전해져 프론트의 재조회와 지연 재확인 헬퍼를 삭제하고 클라이언트 로직을 단순화
05Layer Archive배포 장애 대응 / 2026.07

로컬에서는 통과하고 배포 환경에서만 발생한 조회 오류 해결

H2와 PostgreSQL의 타입 추론 차이를 배포 로그로 추적하고, 실제 데이터베이스를 사용하는 통합 테스트로 재발을 방지했습니다.

문제 원인

  • 배포 환경에서만 GET /api/gallery, GET /api/archives가 항상 500을 반환했습니다. 로컬(H2)에서는 재현되지 않았고 테스트 79개 이상이 모두 통과한 상태였습니다.
  • 서버 로그의 스택트레이스에서 ERROR: function lower(bytea) does not exist를 확인했습니다.
  • 검색어가 없을 때 null이 전달되고, JPQL :search is null or lower(title) like …에서 Postgres가 파라미터 타입을 bytea로 잘못 추론했습니다. H2는 이 추론에 관대해 테스트가 구조적으로 잡을 수 없었습니다.

해결 과정

  • 서비스 계층 normalizeSearch()가 null 대신 빈 문자열을 반환하도록 바꿨습니다.
  • 쿼리 조건을 :search = '' 고정 타입 비교로 바꿔 파라미터가 항상 문자열로 바인딩되게 했습니다.
  • 방언에 민감한 리포지토리 테스트만 Testcontainers Postgres로 전환했습니다(AbstractPostgresIntegrationTest + @ServiceConnection). 나머지는 빠른 H2를 유지했습니다.

결과

  • 배포 환경의 갤러리와 아카이브 목록 조회 장애 해소
  • DB 종류에 따라 달라지는 버그를 사용자가 보기 전에 머지 전 CI에서 잡을 수 있게 됨
  • 검색과 필터 JPQL을 추가할 때 방언 민감도를 먼저 판단하는 기준을 ADR로 문서화
