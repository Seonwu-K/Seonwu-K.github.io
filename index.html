01Poudy데이터 관리 / 2026.08 – 현재

성분 데이터 관리 개선: 정적 파일 방식에서 승인 기반 관리자 시스템으로 전환

정적 파일 수동 관리로 생기던 데이터 불일치와 서버 기동 실패를 막기 위해 승인 기반 관리자 시스템을 구축했습니다. API 기반 검증과 승인 절차를 도입해, 검증된 데이터만 서비스 DB에 반영되는 구조를 마련했습니다.

문제 원인

  • 성분 데이터 원본은 엑셀 파일 하나였고, AI 검수 결과는 실행할 때마다 JSON 파일로 따로 쌓였습니다. 그래서 지금 확정된 값이 무엇인지 한곳에서 볼 수 없었고, 실제로 두 기록의 태그 상태가 서로 달랐습니다.
  • 팀원과 AI가 같은 엑셀 파일을 열다 보니 프로그램마다 서식이 다르게 보였고, 잠금 파일이 남는 일도 잦았습니다.
  • 서버는 켜질 때 데이터 파일 전체를 읽었는데, 미리 검사하는 단계가 없었습니다. 데이터만 바꿨는데 서버가 켜지지 않은 적도 있습니다.

해결 과정

  • 관리자 화면을 만들었습니다. 원료 22,013건을 이름으로 검색하고, 원료마다 현재 상태와 바뀐 내용, 근거, 수정 기록을 볼 수 있습니다.
  • 화면에서 DB를 바로 고치지 않게 했습니다. 변경은 API 요청으로만 할 수 있고, 요청마다 누가 왜 바꿨는지 남습니다. 같은 요청이 두 번 들어와도 한 번만 반영됩니다.
  • 등록된 워크플로, 설정, 정책 버전이 현재 정의와 다르면 요청을 거절합니다. 오래된 규칙으로 데이터를 바꾸는 일을 막기 위해서입니다.
  • 승인된 변경만 확정 데이터에 넣고, 서비스 테이블별 CSV와 manifest로 된 릴리스 파일을 만들었습니다. 이 릴리스를 별도 PostgreSQL에 넣고 실제 서비스 조회 코드로 읽히는지 확인했습니다.

결과

  • 엑셀을 직접 열지 않고 관리자 화면에서 조회, 승인, 반영까지 처리
  • 승인하지 않은 값은 반영되지 않고, 같은 요청을 다시 보내도 두 번 반영되지 않음
  • 두 기록이 서로 달랐던 1,086건은 자동으로 고르지 않고 따로 모아 사람이 확인하도록 함
  • 원료 22,013건을 릴리스 파일로 만들어 별도 DB에 넣고, 다시 넣기와 되돌리기까지 확인
  • 검증은 별도 테스트 DB에서 마쳤고, 운영 DB 반영은 다음 단계로 남겨 두었습니다
02Poudy데이터 파이프라인 / 2026.08 – 현재

LLM 판단과 코드 검증을 분리한 3계층 성분 데이터 파이프라인 구축

성분 데이터를 처리 단계별 3계층(L0 원본 보관, L1 정리와 검토, L2 승인 데이터)으로 나누고, 답이 정해진 검증은 코드가, 판단이 필요한 작업만 LLM이 맡도록 역할을 나눴습니다.

문제 원인

  • 처리 규칙이 파일과 AI 대화 기록에 흩어져 있었습니다. 같은 작업을 다시 돌려도 같은 결과가 나온다는 보장이 없었고, 어떤 규칙으로 처리했는지도 남지 않았습니다.
  • 수집, 정리, 판단, 검토, 반영이 한 흐름에 섞여 있어서 원료 하나에서 막히면 뒤의 작업도 멈췄습니다.
  • 원본과 가공한 결과가 구분되지 않아, 어떤 값이 근거를 갖고 승인된 값인지 나중에 되짚기 어려웠습니다.

해결 과정

  • 데이터를 세 계층으로 나눴습니다. 받은 원본은 고치지 않고 L0에 보관합니다. L1에는 형식을 맞추고 중복과 충돌을 확인한 데이터를 검토 중인 후보로 둡니다. 필드마다 사람 승인과 정책 승인을 모두 통과한 값만 L2로 올립니다. 메달리온 구조를 우리 데이터에 맞게 바꿔 적용했습니다.
  • 단계마다 누가 처리할지 정했습니다. 파일 읽기, 형식 정리, 중복 검사, 릴리스 파일 만들기처럼 답이 정해진 일은 Python 코드가 합니다. 근거 찾기, 설명 쓰기, 검토처럼 판단이 필요한 일만 LLM에게 맡겼습니다.
  • LLM 단계는 LangGraph로 묶어 찾기, 고르기, 쓰기, 검토 순서로 흐르게 했습니다. 관리자 검수가 필요한 건은 체크포인트를 저장하고 멈췄다가(interrupt), 검수가 끝나면 멈춘 지점부터 다시 시작합니다.
  • LLM이 생성한 태그 제안은 LLM 외부의 코드 기반 정책 게이트(policy.py)를 통해 검증합니다. 카탈로그에 존재하지 않는 코드, 근거가 누락되거나 승인되지 않은 참조, 사유 미기재 제안은 코드로 즉시 거절(Reject)합니다. 또한 삭제 요청이나 낮은 확신도(Confidence)의 제안은 자동 반영을 제한하고 휴먼 검증(관리자 검수) 단계로 이관하여 데이터 무결성을 보장했습니다.
  • 작업 순서와 재시도는 SQLite로 관리합니다. 시간 초과처럼 다시 하면 풀리는 실패는 잠시 뒤 재시도하고, 다시 시도해도 결과가 달라지지 않는 실패는 보류로 돌린 뒤 다음 원료를 처리합니다.

결과

  • 원료 22,013건을 같은 규칙, 같은 순서로 처리하는 구조를 만듦
  • 원본 파일, 원료 22,013건, 태그 코드 98종을 기록해 값이 어디서 왔는지 되짚을 수 있게 함
  • 이미 성공한 AI 호출은 결과를 다시 쓰고, 같은 실패는 반복해서 호출하지 않음
  • 같은 작업 기록을 빈 상태에서 두 번 다시 적용해 최종 상태가 같은지 확인
  • 구조 검증과 원료 100건 시험 실행까지 마쳤고, 나머지 원료는 같은 구조로 처리할 예정입니다
03Poudy배포 / 모니터링 / 2026.09

자동 롤백 뒤에 숨은 배포 실패 감지를 위한 인프라 모니터링 체계 도입

자동 롤백으로 배포 실패가 묻히던 문제를 계기로 Prometheus, Grafana, Loki 중심의 모니터링 파이프라인을 도입했습니다. 백엔드 프로세스까지 관측하고 Discord 알림을 연동해, 장애를 팀 전체가 바로 알 수 있는 구조를 마련했습니다.

문제 원인

  • 새 버전에 필요한 검색어 데이터 파일이 빠져, 스테이징 배포부터 백엔드가 켜지지 못했습니다. 제가 만든 배포 파이프라인은 실패하면 자동으로 이전 버전으로 롤백해, 사용자는 오류를 보지 않았습니다.
  • 대신 스테이징과 운영 모두 정상 페이지가 보여, 팀원 누구도 새 코드가 적용되지 않았다는 것을 몰랐습니다. 운영 릴리즈에서도 새 기능이 보이지 않아 파이프라인을 확인하고 나서야, 48시간 전부터 배포 실패와 롤백이 반복되고 있었다는 것을 알았습니다.
  • 기존 모니터링은 CloudWatch와 SNS 이메일로 운영 서버만 보고 있었고, EC2가 멈추지 않는 한 그 안의 백엔드 프로세스가 켜지지 못해도 알 수 없었습니다.

해결 과정

  • 오류 하나로 백엔드 전체가 켜지지 못하는 구조가 근본 문제라고 보고, 팀에 백엔드 예외 처리 구조를 다시 설계하자고 제안했습니다.
  • 예외 처리 개선과 별개로, 같은 장애를 바로 알 수 있도록 모니터링 범위를 넓혔습니다. 모니터링 전용 EC2에 Prometheus, Loki, Grafana를 두고, Frontend와 Backend 서버의 Alloy가 서버 자원, systemd 서비스 상태, 백엔드 프로세스, 로그를 모아 보냅니다. 모니터링 서버는 공개 주소 없이 Cloudflare Tunnel로만 받습니다.
  • 운영만 보던 범위를 스테이징까지 넓히고, Blackbox가 두 환경의 공개 주소를 외부에서 계속 확인하게 했습니다.
  • 알림은 담당자 이메일 대신 팀원 모두가 보는 Discord 공통 채널로 보냅니다. Grafana가 매분 규칙을 평가해, 백엔드 서비스 중단이나 health 확인 실패는 2분, 프로세스 미감지와 메모리 90% 초과는 1분, 디스크 85% 초과는 5분 이어지면 알립니다.

결과

  • 스테이징에서 백엔드를 멈췄을 때 2~3분 안에 팀 Discord로 알림이 오는 것을 확인 (이전 장애는 발견까지 48시간)
  • 관측 범위를 운영 EC2의 생존 여부에서 운영과 스테이징의 프로세스, systemd, 자원, 공개 주소까지 넓히고 알림 규칙 9개를 둠
  • 각 서버에 접속해 보던 로그와 지표를 Grafana 한 화면에서 확인
04Layer Archive동시성 / 멱등성 / 2026.07

동시 요청과 재시도로 발생한 좋아요 오류 해결

같은 사용자의 동시 요청에서 나던 중복 오류를 사용자 행 비관적 락(SELECT … FOR UPDATE)으로 순서대로 처리해 없애고, 토글 API를 원하는 상태를 지정하는 방식으로 바꿔 재시도해도 결과가 같도록(멱등성) 했습니다.

문제 원인

  • 좋아요는 "있는지 확인한 뒤 추가하거나 지우는" 두 단계로 처리됐습니다. 같은 사용자의 요청이 동시에 들어오면 둘 다 "없음"으로 읽고 함께 추가하려다 중복 제약에 걸렸습니다.
  • API가 현재 상태를 뒤집는 토글 방식이라, 응답이 늦어 사용자가 다시 누르면 두 번째 요청이 방금 누른 좋아요를 지웠습니다.
  • 처음에는 추가만 별도 트랜잭션으로 떼어 오류를 흡수했지만, 그러면 API는 실패를 돌려주는데 좋아요는 남는 불일치가 생길 수 있었습니다.

해결 과정

  • 별도 트랜잭션을 없애고 한 트랜잭션에서 처리해, 실패하면 전부 되돌아가게 했습니다.
  • 요청한 사용자의 행에 잠금을 걸어(SELECT … FOR UPDATE) 같은 사용자의 좋아요 요청이 한 번에 하나씩 처리되게 했습니다. 상점 구매 기능에서 이미 쓰던 잠금 방식과 맞춰, 서비스 안의 동시성 처리 방식을 하나로 통일했습니다.
  • 토글 API를 원하는 최종 상태를 지정하는 API(PUT, liked: true 또는 false)로 바꿨습니다. 이미 같은 상태면 아무것도 바꾸지 않아, 몇 번을 보내도 결과가 같습니다.
  • 변경 단계별 Git 커밋에서 같은 동시성 테스트를 다시 실행해, 동시 요청과 재시도 결과를 비교했습니다.

결과

  • 같은 사용자의 좋아요 요청 5개를 동시에 50번 보냈을 때 실패 250건 중 200건 → 0건 (잠금 적용 전후)
  • 좋아요를 누른 뒤 같은 요청을 다시 보냈을 때 좋아요가 남은 비율 0% → 100% (토글 API와 상태 지정 API, 50번)
  • 재시도가 항상 안전해져 화면의 재조회와 지연 재확인 로직을 지우고 단순하게 정리
  • 측정 환경은 PostgreSQL 16이며, 요청마다 별도 트랜잭션으로 서비스를 호출했습니다
05Layer Archive조회 성능 / 2026.07

목록 조회의 N+1 쿼리 해결 (53회 → 4회)

목록에는 필요 없는 이미지 연관관계를 게시글마다 따로 불러오던 N+1 문제를 목록 전용 응답 DTO로 분리해 해결하고, 게시글 50건 기준 쿼리 수를 53회에서 4회로 줄였습니다.

문제 원인

  • 갤러리 목록 API가 게시글 엔티티를 이미지 목록까지 담는 응답으로 그대로 바꾸고 있었습니다. 이미지 목록은 필요할 때 읽는 지연 로딩이라, 게시글 50건이면 이미지 조회가 50번 더 나갔습니다.
  • 목록 화면은 대표 이미지 한 장만 쓰는데, 게시글에 달린 이미지를 전부 불러오고 있었습니다.
  • 목록도 한 번에 전부 받아 화면에서 나누고 있어서, 게시글이 늘수록 한 번에 읽는 양이 함께 늘어나는 구조였습니다.

해결 과정

  • 이미지 목록을 뺀 목록 전용 응답 DTO을 따로 만들고, 이미지 전체는 상세 조회에서만 담게 나눴습니다.
  • 목록 조회는 작성자와 카테고리만 함께 가져오고(fetch join), 좋아요 수와 태그는 게시글 ID 목록으로 한 번에 모아 조회합니다.
  • 서버 페이징을 도입해 한 번에 최대 50건만 읽게 했습니다.
  • 이미지를 함께 담는 기존 응답(마이페이지 목록)을 비교군으로 두고, 같은 데이터에서 쿼리 수와 처리 시간을 측정했습니다.

결과

  • 게시글 50건 기준 쿼리 53회 → 4회
  • 응답 시간 중앙값 약 11ms → 3.5ms (300회씩 3번 측정)
  • 게시글 수가 늘어도 목록 조회의 쿼리 수가 늘지 않는 구조로 변경
  • 측정 환경은 PostgreSQL 16, 게시글당 이미지 3장이며, 네트워크를 뺀 애플리케이션 처리 시간입니다
