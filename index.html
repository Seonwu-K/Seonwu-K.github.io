01Poudy데이터 관리 / 2026.08 – 현재

성분 데이터 관리 개선: 정적 파일 방식에서 승인 및 검증 기반 관리 시스템으로 전환

정적 파일 수동 관리로 생기던 데이터 불일치와 검증 없는 반영을 막기 위해 승인 기반 관리자 시스템을 구축했습니다. API 기반 검증과 승인 절차를 도입해, 검증된 데이터만 서비스 DB에 반영되는 구조를 마련했습니다.

문제 원인

  • 성분, 제품 데이터와 AI 검수 결과가 엑셀과 파일 단위로 흩어져, 최신 상태와 변경 이력을 추적하기 어려웠습니다.
  • 파일을 직접 고치는 방식이라 누가 왜 바꿨는지 남지 않았습니다.
  • 이전 태그 DB와 AI 검수 결과가 달라도 자동으로 구분되지 않아, 어떤 값을 검토해야 하는지 사람이 직접 찾아야 했습니다.
  • 파일 변환, S3 업로드까지 서비스 반영 과정이 수작업이었고, 반영 전 검증 단계도 없었습니다.
  • LLM 검수에 드는 토큰과 처리 시간을 기록하지 않아 병목 지점과 비효율을 파악하기 어려웠습니다.

해결 과정

  • 원료 22,013건의 상태, 변경 내용, 근거, 수정 이력을 확인하고 승인할 수 있는 관리자 화면을 구축했습니다.
  • 모든 변경을 API 요청으로만 처리하고 요청자와 사유를 남겨, 같은 요청이 반복돼도 한 번만 반영되도록 설계했습니다.
  • 이전 태그 DB와 AI 검수 결과를 비교해 불일치를 자동으로 찾아내고, 값은 자동으로 고르지 않고 검토 대상으로 분리했습니다.
  • 승인된 데이터만 확정 데이터로 반영하고, CSV와 manifest로 된 릴리스 파일을 만들어 별도 DB에서 검증하는 절차를 만들었습니다.
  • LLM 호출별 입력, 출력 토큰과 처리 시간을 기록하고 시각화해, 비용이 큰 작업과 병목 구간을 찾을 수 있게 했습니다.

결과

  • 원료 22,013건을 관리자 화면에서 조회, 승인, 릴리스까지 처리하는 운영 흐름 구축
  • 모든 변경의 요청자와 사유가 기록되고, 같은 요청을 다시 보내도 두 번 반영되지 않음
  • 이전 태그 DB와 AI 검수 결과가 다른 1,086건을 자동으로 찾아 검토 대상으로 분리
  • 릴리스 생성, 별도 DB 적재, 조회, 되돌리기까지 검증 (운영 DB 반영은 다음 단계)
  • 호출 기록으로 병목이 코드가 아니라 LLM 호출이라는 것을 수치로 확인
02Poudy데이터 파이프라인 / 2026.08 – 현재

LLM 판단과 코드 검증을 분리한 3계층 성분 데이터 파이프라인 구축

성분 데이터를 처리 단계별 3계층(L0 원본 보관, L1 정리와 검토, L2 승인 데이터)으로 나누고, 답이 정해진 검증은 코드가, 판단이 필요한 작업만 LLM이 맡도록 역할을 나눴습니다.

문제 원인

  • 원료 한 건의 수집, 가공, 검증과 작업 조율까지 Codex 모델 하나에 맡겨, 3일 동안 Pro 사용 한도를 초기화 3번까지 모두 쓰고도(기본 한도의 4배) 서비스에 쓸 만한 데이터를 얻지 못했습니다.
  • 처리와 검증 역할이 나뉘지 않아, 사람이 개입하지 못하는 동안 실패하는 데이터 하나에 걸리면 LLM이 같은 시도를 반복하며 다음 데이터로 넘어가지 못한 채 시간과 토큰만 썼습니다.
  • 원본과 가공 결과가 섞여 값의 출처와 승인 근거를 추적하기 어려웠습니다.

해결 과정

  • 한 건씩이 아니라 전체 데이터를 배치로 처리하도록 수집 파이프라인을 다시 설계하고, 원본, 정리와 검토 후보, 승인 데이터로 나눈 메달리온 구조(L0~L2)를 적용했습니다.
  • 파일 처리, 형식 정리, 중복 검사처럼 규칙이 명확한 일은 Python 코드가, 근거 찾기, 설명 쓰기, 검토처럼 판단이 필요한 일만 LLM이 맡도록 나눴습니다.
  • LLM 단계는 LangGraph로 찾기, 고르기, 쓰기, 검토로 나누고, 결과는 코드로 된 정책 게이트를 통과해야 반영되게 했습니다. 근거가 없거나 확신도가 낮은 제안은 자동 반영하지 않고 관리자 검수로 처리합니다.
  • 작업 상태와 호출 기록을 저장해 성공한 호출은 재사용하도록 설계했습니다. 시간 초과처럼 일시적인 실패는 재시도하고, 다시 해도 같은 결과가 나오는 실패는 사유를 기록해 DLQ처럼 별도 경로로 빼 두어, 에이전트가 멈추지 않고 다음 원료를 이어서 처리하도록 설계했습니다.

결과

  • 원료 22,013건을 같은 규칙으로 처리하는 배치 파이프라인 구축
  • 출처와 승인 이력을 남겨 값이 어디서 왔는지 추적 가능
  • 성공한 호출은 재사용하고 막히는 데이터는 따로 빼 두어, 한 건에 걸려 토큰만 쓰며 멈추던 문제 해소
  • 원료 100건 시험 실행까지 마쳤고, 나머지 원료는 같은 구조로 처리할 예정입니다
03Poudy배포 / 모니터링 / 2026.09

자동 롤백 뒤에 숨은 배포 실패 감지를 위한 인프라 모니터링 체계 도입

자동 롤백으로 배포 실패가 묻히던 문제를 계기로 Prometheus, Grafana, Loki 중심의 모니터링 파이프라인을 도입했습니다. 백엔드 프로세스까지 관측하고 Discord 알림을 연동해, 장애를 팀 전체가 바로 알 수 있는 구조를 마련했습니다.

문제 원인

  • 검색어 데이터 파일을 S3에 올려 두지 않아 스테이징부터 백엔드가 기동하지 못했지만, 배포 파이프라인이 자동으로 롤백해 화면은 정상으로 보였습니다.
  • 팀 누구도 새 코드가 반영되지 않은 것을 몰라, 48시간 동안 배포 실패와 롤백이 반복됐습니다.
  • 기존 모니터링(CloudWatch, SNS 이메일)은 운영 EC2가 살아 있는지만 봐서, 서버는 살아 있고 백엔드 프로세스만 멈춘 장애를 감지하지 못했습니다.

해결 과정

  • 예외 처리 개선은 팀에 제안하고, 이와 별개로 프로세스 수준 장애를 바로 감지하도록 모니터링을 다시 설계했습니다.
  • Prometheus, Loki, Grafana와 Alloy로 프로세스, systemd 상태, 서버 자원, 로그를 한곳에서 관측하도록 구성했습니다.
  • 운영만 보던 범위를 스테이징까지 넓히고, Blackbox로 공개 주소에 실제로 접속되는지 외부에서 확인했습니다.
  • 장애 기준별 Grafana 알림 규칙 9개를 두고, 담당자 이메일 대신 팀 공용 Discord 채널로 알림을 모았습니다.

결과

  • 스테이징에서 백엔드를 멈췄을 때 2~3분 안에 팀 Discord로 알림이 오는 것을 확인 (이전 장애는 발견까지 48시간)
  • 관측 범위를 EC2 생존 여부에서 프로세스, systemd, 자원, 외부 접근 상태까지 확대
  • 각 서버에 접속하지 않고 Grafana 한 화면에서 로그와 주요 지표 확인
04Layer Archive동시성 / 멱등성 / 2026.07

비관적 락과 상태 지정 API로 좋아요 동시성과 재시도 오류 해결

같은 사용자의 동시 요청에서 나던 중복 오류를 사용자 행 비관적 락(SELECT … FOR UPDATE)으로 순서대로 처리해 없애고, 토글 API를 원하는 상태를 지정하는 방식으로 바꿔 재시도해도 결과가 같도록(멱등성) 했습니다.

문제 원인

  • 좋아요는 "있는지 확인한 뒤 추가하거나 지우는" 두 단계로 처리됐습니다. 같은 사용자의 요청이 동시에 들어오면 둘 다 "없음"으로 읽고 함께 추가하려다 중복 제약에 걸렸습니다.
  • API가 현재 상태를 뒤집는 토글 방식이라, 응답이 늦어 사용자가 다시 누르면 두 번째 요청이 방금 누른 좋아요를 지웠습니다.
  • 처음에는 추가만 별도 트랜잭션으로 떼어 오류를 흡수했지만, 그러면 API는 실패를 돌려주는데 좋아요는 남는 불일치가 생길 수 있었습니다.

해결 과정

  • 별도 트랜잭션을 없애고 한 트랜잭션에서 처리해, 실패하면 전부 되돌아가게 했습니다.
  • 요청한 사용자의 행에 잠금을 걸어(SELECT … FOR UPDATE) 같은 사용자의 좋아요 요청이 한 번에 하나씩 처리되게 했습니다. 상점 구매 기능에서 이미 쓰던 잠금 방식과 맞춰, 서비스 안의 동시성 처리 방식을 하나로 통일했습니다.
  • 토글 API를 원하는 최종 상태를 지정하는 API(PUT, liked: true 또는 false)로 바꿨습니다. 이미 같은 상태면 아무것도 바꾸지 않아, 몇 번을 보내도 결과가 같습니다.
  • 변경 단계별 Git 커밋에서 같은 동시성 테스트를 다시 실행해, 동시 요청과 재시도 결과를 비교했습니다.

결과

  • 같은 사용자의 좋아요 요청 5개를 동시에 50번 보냈을 때 실패 250건 중 200건 → 0건 (잠금 적용 전후)
  • 좋아요를 누른 뒤 같은 요청을 다시 보냈을 때 좋아요가 남은 비율 0% → 100% (토글 API와 상태 지정 API, 50번)
  • 재시도가 항상 안전해져 화면의 재조회와 지연 재확인 로직을 지우고 단순하게 정리
  • 측정 환경은 PostgreSQL 16이며, 요청마다 별도 트랜잭션으로 서비스를 호출했습니다
05Layer Archive조회 성능 / 2026.07

목록 조회의 N+1 쿼리 해결 (53회 → 4회)

목록에는 필요 없는 이미지 연관관계를 게시글마다 따로 불러오던 N+1 문제를 목록 전용 응답 DTO로 분리해 해결하고, 게시글 50건 기준 쿼리 수를 53회에서 4회로 줄였습니다.

문제 원인

  • 갤러리 목록 API가 게시글 엔티티를 이미지 목록까지 담는 응답으로 그대로 바꾸고 있었습니다. 이미지 목록은 필요할 때 읽는 지연 로딩이라, 게시글 50건이면 이미지 조회가 50번 더 나갔습니다.
  • 목록 화면은 대표 이미지 한 장만 쓰는데, 게시글에 달린 이미지를 전부 불러오고 있었습니다.
  • 목록도 한 번에 전부 받아 화면에서 나누고 있어서, 게시글이 늘수록 한 번에 읽는 양이 함께 늘어나는 구조였습니다.

해결 과정

  • 이미지 목록을 뺀 목록 전용 응답 DTO을 따로 만들고, 이미지 전체는 상세 조회에서만 담게 나눴습니다.
  • 목록 조회는 작성자와 카테고리만 함께 가져오고(fetch join), 좋아요 수와 태그는 게시글 ID 목록으로 한 번에 모아 조회합니다.
  • 서버 페이징을 도입해 한 번에 최대 50건만 읽게 했습니다.
  • 이미지를 함께 담는 기존 응답(마이페이지 목록)을 비교군으로 두고, 같은 데이터에서 쿼리 수와 처리 시간을 측정했습니다.

결과

  • 게시글 50건 기준 쿼리 53회 → 4회
  • 응답 시간 중앙값 약 11ms → 3.5ms (300회씩 3번 측정)
  • 게시글 수가 늘어도 목록 조회의 쿼리 수가 늘지 않는 구조로 변경
  • 측정 환경은 PostgreSQL 16, 게시글당 이미지 3장이며, 네트워크를 뺀 애플리케이션 처리 시간입니다
