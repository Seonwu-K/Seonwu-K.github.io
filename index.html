01Layer Archive그림 수업 관리 시스템 | 실서비스 운영 | 2026.07 – 2026.08

동시 좋아요 요청의 경합과 재시도 불안정을 User 행 비관적 락과 멱등 PUT API로 해결

문제 원인

  • "좋아요 존재 여부 확인 → INSERT/DELETE" 사이에 경합이 있어, 같은 사용자의 동시 요청 5개만으로 unique 제약 위반 500이 재현됐습니다.
  • 토글(현재 상태 반전) API는 멱등하지 않아, 응답이 늦어 사용자가 재시도하면 두 번째 요청이 첫 요청이 추가한 좋아요를 삭제했습니다.
  • 클라이언트의 재조회와 지연 재확인 같은 타이밍 기반 완화는 서버 처리가 길어지면 다시 잘못된 재시도를 유도했고, Codex 코드 리뷰에서도 같은 결함이 반복 지적됐습니다.

해결 과정

  • 좋아요 삽입을 REQUIRES_NEW로 분리하던 방식을 걷어내고 같은 트랜잭션에서 처리해, 요청이 실패해도 절반만 반영된 상태가 남지 않게 했습니다.
  • UserRepository.findByIdForUpdate()로 요청 사용자 행에 비관적 락을 걸어 같은 사용자의 좋아요 요청을 직렬화했습니다. 상점 구매와 보상 회수에서 쓰던 패턴과 맞췄습니다.
  • POST 토글을 PUT /like {"liked": true|false} "원하는 최종 상태 지정" API로 재설계하고, setLiked()는 현재 상태와 같으면 아무것도 하지 않도록 했습니다.
  • 실제 Postgres에 동시 요청을 라운드 단위로 반복 전송해 검증하고, 멱등성 통합 테스트를 추가했습니다.

결과

  • 락 도입 후 동일 세션 10개 동시 요청 × 5라운드(50건) 전부 200 성공
  • 같은 liked=true를 10개 동시 × 3라운드 보내도 likeCount가 항상 1로 수렴
  • 재시도가 항상 안전해져 프론트의 재조회와 지연 재확인 헬퍼를 삭제하고 클라이언트 로직을 단순화
02Layer Archive배포 장애 대응 | 2026.07

H2에서만 통과하던 JPQL 타입 추론 차이를 배포 로그로 추적해 수정하고, Testcontainers Postgres 통합 테스트로 재발 방지

문제 원인

  • 배포 환경에서만 GET /api/gallery, GET /api/archives가 항상 500을 반환했습니다. 로컬(H2)에서는 재현되지 않았고 테스트 79개 이상이 모두 통과한 상태였습니다.
  • 서버 로그의 스택트레이스에서 ERROR: function lower(bytea) does not exist를 확인했습니다.
  • 검색어가 없을 때 null이 전달되고, JPQL :search is null or lower(title) like …에서 Postgres가 파라미터 타입을 bytea로 잘못 추론했습니다. H2는 이 추론에 관대해 테스트가 구조적으로 잡을 수 없었습니다.

해결 과정

  • 서비스 계층 normalizeSearch()가 null 대신 빈 문자열을 반환하도록 바꿨습니다.
  • 쿼리 조건을 :search = '' 고정 타입 비교로 바꿔 파라미터가 항상 문자열로 바인딩되게 했습니다.
  • 방언에 민감한 리포지토리 테스트만 Testcontainers Postgres로 전환했습니다(AbstractPostgresIntegrationTest + @ServiceConnection). 나머지는 빠른 H2를 유지했습니다.

결과

  • 배포 환경의 갤러리와 아카이브 목록 조회 장애 해소
  • 같은 유형의 방언 차이 버그를 사용자에게 노출되기 전 머지 전 CI에서 잡는 구조 확보
  • 검색과 필터 JPQL을 추가할 때 방언 민감도를 먼저 판단하는 기준을 ADR로 문서화
03Layer Archive성능 진단 | 2026.07 – 2026.09

API 기본 응답 0.44초의 원인을 경로별 구간 측정으로 좁히고, 틀린 첫 가설을 재측정으로 반증해 설정 한 줄로 해결

문제 원인

  • DB를 전혀 쓰지 않는 헬스체크조차 0.4~0.5초가 걸려, 애플리케이션 로직이 아니라 네트워크 구간의 고정 비용으로 판단했습니다.
  • 첫 가설(백엔드가 미국 리전에 있어서 느리다)에 따라 백엔드를 서울 EC2로 옮겼지만, 재측정해 보니 지연이 그대로였습니다.
  • 같은 백엔드를 두 경로로 호출해 구간을 가르자 프록시 경유 0.44초, 직접 호출 0.04초였습니다. Vercel 함수가 기본 리전 iad1(워싱턴 DC)에서 실행돼 매 요청이 태평양을 왕복하고 있었습니다.

해결 과정

  • DB 미사용 헬스체크 → 경로별 측정 순서로 병목 구간을 Vercel 함수 구간까지 좁혔습니다.
  • 백엔드만 서울로 옮기면서 오히려 함수와 백엔드 사이 왕복이 늘었다는 점을 확인하고, frontend/vercel.json에 "regions": ["icn1"]를 지정했습니다.
  • 조치 전과 같은 경로를 다시 측정해 개선을 확인했습니다.

결과

  • /api/health(프록시 경유) 0.44초 → 0.07~0.11초
  • /api/gallery(DB 조회 포함) 0.46~0.48초 → 0.10~0.19초, 요청당 약 0.35초, 4~5배 개선
  • 코드 변경 없이 설정 한 줄로 해결. 인프라 이전을 끝으로 보지 않고 재측정으로 가설을 검증
04LinkZipUMC 6기 데모데이 대상 | 백엔드 리드 | 2024.07 – 2024.08

URL을 직접 읽지 못하는 GPT API의 한계를 서버 측 HTML 정보 추출로 보완해 링크 요약 핵심 기능 완성

문제 원인

  • 링크만 모아 두면 나중에 무슨 내용인지 알 수 없어 다시 열어 봐야 했고, 그래서 저장할 때 요약을 함께 보여주는 것이 서비스의 핵심 기능이었습니다.
  • 당시 API로 쓸 수 있던 GPT 모델은 URL을 전달해도 페이지를 직접 열어 읽지 못했습니다.
  • 팀 안에서 "구현이 어려우면 빼도 된다"는 의견이 나왔지만, 이 기능이 빠지면 단순 링크 보관 서비스만 남는 상황이었습니다.

해결 과정

  • AI에 주소를 넘기는 대신 서버가 먼저 페이지를 받아오도록 구조를 바꿨습니다. axios로 HTML을 받고 cheerio로 title, meta description, 첫 h1, 첫 문단을 추출했습니다.
  • 추출한 텍스트를 프롬프트와 함께 OpenAI API에 전달해 요약을 받고, 링크 메타데이터와 함께 MySQL에 저장했습니다.
  • https 요청이 실패하면 http로 재시도하고, YouTube 링크는 영상 요약 API 결과를 GPT로 한국어 정리하도록 분기했습니다.

결과

  • 포기할 뻔한 핵심 기능을 마감 안에 완성
  • UMC 6기 데모데이 약 60개 팀 중 대상(1위)
  • 백엔드 리드로 Express 아키텍처, MySQL 스키마, AWS 배포까지 전 과정 주도
05IT 뉴스 RAG 챗봇졸업 캡스톤 | 개인 개발 | 2025.03 – 2025.06

단순 프롬프팅의 할루시네이션을 학습이 필요 없는 RAG로 줄이고, 평가 지표와 테스트셋을 직접 설계해 효과를 정량 검증

문제 원인

  • 뉴스 기반 질의응답에서 단순 AI 프롬프팅은 그럴듯하지만 기사에 없는 내용을 지어내는 할루시네이션을 보였습니다.
  • 자체 모델 학습은 인적, 시간 자원이 부족해 현실적인 선택지가 아니었습니다.
  • 개선했다고 말하려면 "좋아진 것 같다"가 아니라 객관적으로 비교할 평가 기준이 필요했습니다.

해결 과정

  • IT 뉴스 3,385건을 크롤링해 전처리하고 Upstage 임베딩으로 ChromaDB에 저장했습니다.
  • 질문과 관련된 기사를 먼저 검색해 근거로 함께 전달하는 RAG 파이프라인을 LangChain으로 구성하고, Solar LLM으로 답변을 생성했습니다.
  • 정확도, 관련성, 환각률 지표와 논문 평가용 테스트 데이터셋을 직접 설계하고, 프롬프팅 기법 4종을 템플릿으로 모듈화해 함께 비교했습니다.

결과

  • RAG 적용 전후 정확도 82% → 93%, 관련성 85% → 95%, 환각률 46.7% → 8.5%
  • 프롬프팅 기법 비교에서는 요약 간결성, 정확성, 정보 풍부함 등 상황에 따라 최적 전략이 달라진다는 결론 도출
  • 졸업논문으로 발표하고 캡스톤 최종 통과
